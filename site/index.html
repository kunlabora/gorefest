Game days have a picking problem

  • The shelf is long, the day isn't

    Everyone brings their favourites. By the time the group has read every box, there's time for one game fewer.

    Boardfest: only games that fit who's at the table and the time you have left.

  • Nobody wants to pick

    The quiet ones go along with whatever the loudest player suggests, and the same three games come out every time.

    Boardfest: it ranks for the whole table, so nobody gets stuck with a game they'll hate.

  • Taste is invisible

    You know you like heavy euros. Your friends don't, and you've never seen half their shelf.

    Boardfest: twelve quick pairs make a taste profile, and every game played sharpens it.

Under the hood

Boring tech, sharp edges

Kotlin on the JVM, Ktor, Postgres, and HTML rendered on the server. No SPA, no build step for the front end, no framework for the domain. Three ideas carry most of the weight.

1Event sourcing with a Dynamic Consistency Boundary

Every change is an event in one global log: GameBrought, ComparisonRecorded, PlayLogged. There are no aggregates. Each decision says exactly which events it depends on, as a query on event types and tags, and only those events can conflict with it.

Appending takes a Postgres advisory lock, checks that nothing matching the query arrived after the decision read the log, and inserts. Two players ticking games at the same moment never block each other, while the "3 wishes per game day" limit still holds when two people ask at once.

Read models are in memory, rebuilt by replaying the log on startup. Swapping the taste model was a matter of replaying the same comparisons through a new algorithm and comparing the predictions.

2HTML from Kotlin, with htmx

Pages are written in kotlinx.html, a type-safe Kotlin DSL for HTML. A view is a plain function, so the compiler checks it, it composes like any other code, and a component is just another function.

htmx swaps one fragment per interaction: tick who's at the table and the server answers with the new #suggestions. Every handler answers an htmx request with a fragment and a plain request with a full page, so everything also works without JavaScript.

Tests parse the HTML with Jsoup and assert on CSS selectors, never on substrings.

3Functional core, imperative shell

Everything that decides something lives in gorefest.core: events, deciders, read models, the taste model and the matcher. The core is pure. No database, no HTTP, no clock, no random numbers: whatever a decision needs, like the ids, today's date and who's acting, arrives in the command.

Everything with side effects lives in gorefest.shell: Postgres, the event store, BoardGameGeek's XML API, mail and the web. The shell builds a command, calls the core and stores what the core decided.

So the core is tested as given / when / then, with no mocks, and these rules aren't just advice. ArchitectureTest (Konsist) fails the build when the core imports the shell, reads the clock or calls Uuid.random().

Accessible by construction

WCAG isn't a checklist at the end

A game day happens in dim rooms, on old phones, inside the WhatsApp browser, and some players use a screen reader. Making each page accessible by hand doesn't last. So the code makes the inaccessible version hard to write, and the build fails when someone writes it anyway.

  1. 1

    Promises in the Contract

    The A11Y area states WCAG 2.2 AA's basics as obligations, like "every form control has a label tied to it" and "when htmx swaps something in, a screen reader hears what changed". Each one has a test.

  2. 2

    Components carry the labels

    field, actionButton, image and their friends render the label, the name and the ARIA wiring. A name can't be blank: AccessibleName refuses it when the page is built.

  3. 3

    Views can't go around them

    ArchitectureTest fails when a view calls input, button or img itself, writes aria-* or role, or writes a heading without the component that takes its level.

  4. 4

    Every test checks every page

    The web tests' page() and fragment() parse each response and check that every control has a name, ids are unique, labels point at ids that exist, grouped choices are named and every <nav> has a label.

The design system does its part too. Every text colour pair meets 4.5:1 in both themes, and control borders and focus rings meet 3:1. Tap targets are at least 44px. Selection never relies on colour alone. Reduced-motion settings turn the animations off, and body text is set in Atkinson Hyperlegible Next, a typeface made for low-vision readers. Running it

One small server on Scaleway

A friend group doesn't need Kubernetes. Boardfest runs as one fat jar on one of Scaleway's smallest instances in Paris, and every push to main goes live a few minutes later.

  1. 1

    Push to main

    GitHub Actions runs ./gradlew check: tests against a real Postgres in Testcontainers, the Contract coverage, the architecture rules and detekt. Then it builds the fat jar.

  2. 2

    Copy and switch

    The jar goes over scp into a new timestamped release folder. A symlink moves to it and systemd restarts the service.

  3. 3

    Healthy, or roll back

    deploy.sh waits for /health while the app replays the event log. If the new release doesn't come up, the symlink goes back and the old release restarts. The five newest releases are kept.

  4. 4

    Caddy in front

    Caddy terminates TLS and renews its own certificate. Nightly, a systemd timer runs pg_dump to Scaleway Object Storage. Login mail goes out through Scaleway Transactional Email.

Set up in an afternoon

deploy/scaleway.md walks through it step by step: a DEV1-S instance on Ubuntu, an SSH key just for GitHub Actions, the DNS record, SPF and DKIM for mail, an API key and a backup bucket. provision.sh does the rest on the server, including the firewall, the service user and journald's 14-day log retention.

European, private, small

The server, the backups and the login mail run on Scaleway, in the EU. The site tells search engines to stay away, and the admin approves every new account. Erasing an account anonymises it in the log, and a restore from backup re-applies the erasures. It's a closed circle of friends, and the setup is built to keep it that way.

How it's built

Impatient Programming

Boardfest is mostly written by AI agents, following Impatient Programming (IMP): Extreme Programming applied to agentic development. Code is cheap now, so what counts is what the code promises and the machines that check it. Here's how this repo puts the rules into practice.

  • 305obligations in the Contract
  • 600+@Obligation tags on tests
  • 12areas, from accounts to accessibility

  • The Contract

    What the app promises, as numbered obligations per area, each one plain sentence: GD-1 Only the host changes a game day's title, date and place. Every obligation is proven by a test tagged @Obligation("GD-1"), and ContractCoverageTest fails the build when an obligation has no test. Ids are forever: a dropped one is struck through, never reused.

  • Machines enforce the standards

    A convention a machine can check goes into ArchitectureTest, not only into a README: the core stays pure, deciders are objects, every event has a stored name and tags, views don't touch the database. detekt runs on every push, and its baseline may only shrink. Mutation testing with pitest, plus a kill matrix, shows which tests actually catch anything.

  • Bugs are gaps in the Contract

    A bug in production means a promise was missing. The bug skill writes the obligation first, then a test that fails on the bug, then the fix. Only that kind of commit starts with fix:. Everything else is refine:, so the log shows how often production broke.

  • Guardrails on the agent

    Claude Code hooks ask before a push (pushing main deploys), before changing a Flyway migration, before renaming a stored event type, before dropping a Contract id and before growing the detekt baseline. A mistake an agent makes twice gets a check.

  • Skills for the loop

    story takes a backlog item from criteria to commit. spike builds two or three options in throwaway worktrees and compares them. regen-check rebuilds a decider from its obligations alone, to find the promises the Contract forgot to state.

  • Fresh eyes, then breathe out

    The adversarial-review agent gets a commit range and nothing else, and tries to break the change against the Contract. Afterwards exhale folds what the change taught back into the code, without changing behaviour, so the codebase stays as simple as it was.

Boardfest is private. It runs for one group of friends, and there's no public instance to sign up for. The code is open under the MIT licence, so you can run your own for your group.
