Chapter 1 of 6

Picking a game takes too long

Eight friends stand around forty games and spend an hour saying "I don't mind, what do you want?".

There are too many games
Boardfest only suggests games that work for the people at the table and fit the time you have.
Nobody wants to pick
It ranks the games for everyone at the table. The loudest player gets no extra say.
Nobody knows what the others like
You answer about a dozen "which of these two?" questions. After each game you play, it asks one more.

Chapter 3 of 6

How it's built

Kotlin, Ktor and Postgres, with the HTML rendered on the server. There's no single-page app and no framework in the domain code. Three things are worth knowing before you open it.

1

One event log, no aggregates

Every change is an event, like GameBrought or ComparisonRecorded. Each decision lists the events it depends on (a Dynamic Consistency Boundary), and only those can conflict with it. Read models live in memory and are rebuilt from the log on startup.

Show the code 
object BringGameDecider : Decider<BringGame, BringState, Event> {
    // Only this player bringing this game is inside the boundary,
    // so everyone can tick games at once.
    override fun query(command: BringGame) = Query.of(
        Query.Item(setOf(GameDayCreated, GameDayEnded, GameDayCancelled),
            setOf(gameDay(command.gameDay))),
        Query.Item(setOf(PlayerJoined),
            setOf(gameDay(command.gameDay), player(command.player))),
        Query.Item(setOf(GameBrought, GameUnbrought),
            setOf(gameDay(command.gameDay), player(command.player), game(command.game))),
    )

    override fun decide(command: BringGame, state: BringState) = when {
        !state.joined -> Rejected(Rejection.NotJoined)
        command.bringing == state.bringing -> Accepted()
        command.bringing -> Accepted(GameBrought(command.gameDay, command.player, command.game))
        else -> Accepted(GameUnbrought(command.gameDay, command.player, command.game))
    }
}

2

HTML written in Kotlin

Views are Kotlin functions written with kotlinx.html. The compiler checks them, and a component is a function like any other. htmx swaps in one fragment per click, and the pages work without it too.

fun TagConsumer<*>.suggestions(view: TableView) = section("gf-picker__answer") {
    id = "suggestions"
    announce(view.announcement())
    when (val suggestions = view.suggestions) {
        is Suggestions.Found -> suggestions.top.forEachIndexed { i, s ->
            rankedGame(i + 1, s.game, s.reason.text())
        }
        is Suggestions.NothingFits ->
            emptyState(suggestions.title(), suggestions.text())
    }
}

3

A pure core, a thin shell

gorefest.core decides: no database, no clock, no randomness. gorefest.shell does the IO: Postgres, BoardGameGeek, mail and the web. Core tests are given / when / then, with no mocks. An architecture test fails the build if the core imports anything from the shell.

Shell

web · Postgres · BGG · mail · clock

Core

deciders · read models · taste · matcher

Chapter 4 of 6

Accessible by construction

People use the app in dim rooms and on old phones, and some use a screen reader. The code makes an inaccessible page hard to write, and the build fails if you manage it anyway.

  1. The Contract. The basics of WCAG 2.2 AA are obligations there, each with a test.
  2. Components. Shared ones like field and actionButton add the labels and ARIA for you, and won't take a blank name.
  3. Architecture test. It fails when a view writes a raw input, button, img or aria-* itself.
  4. Web tests. Each one parses the page it gets back and checks names, unique ids, labels and heading order.

Chapter 5 of 6

One small server on Scaleway

A group of friends doesn't need Kubernetes. The app is one fat jar on a small Scaleway instance in Paris. A push to main is live a few minutes later.

  1. PushGitHub Actions runs every check and builds the jar.
  2. InstallThe jar goes into a new release folder and systemd restarts the app.
  3. CheckIf /health doesn't answer, the deploy rolls back to the previous release.
  4. RunCaddy handles TLS. pg_dump makes a backup every night.

deploy/scaleway.md walks through the setup, and provision.sh does the rest on the server.

Chapter 6 of 6

How we work: Impatient Programming

AI agents write most of Boardfest. We follow Impatient Programming, which is Extreme Programming adapted to working with agents. Writing code is cheap now. The real work is saying what the app must do and testing that it does.

The Contract
305 numbered promises, like GD-1 Only the host changes a game day's title, date and place. Each has a tagged test, and the build fails if one doesn't.
Rules live in tests
If a machine can check a convention, it goes into an architecture test. Mutation testing shows which tests actually catch anything.
A bug is a missing promise
Add the promise, then a test that fails, then the fix. Only bug fixes for production start with fix:.
Hooks and skills
Hooks ask before a push or a risky change. Skills such as story, bug and spike walk an agent through the work. There's also an adversarial review agent, and exhale to tidy up afterwards.

Your first hour

  1. Run it. Start Postgres with podman compose up -d, then the jar. Dev mode sends no real mail. Login mail shows up at /dev/mailbox.
  2. Check it. ./gradlew check runs the tests, the Contract, the architecture rules and detekt.
  3. Read two things. CLAUDE.md has the vocabulary and conventions. docs/contract/ has what the app promises.
  4. Pick a story. docs/backlog.md says what's up next.
