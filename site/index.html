Chapter 3 of 6

How it's built

Kotlin, Ktor and Postgres, with HTML rendered on the server. No SPA and no framework for the domain. Three ideas carry most of the weight.

1

One event log, no aggregates

Every change is an event, like GameBrought or ComparisonRecorded. Each decision names exactly the events it depends on (a Dynamic Consistency Boundary), so only those can conflict with it. Read models are rebuilt in memory on startup.

Show the code 
object BringGameDecider : Decider<BringGame, BringState, Event> {
    // Only this player bringing this game is inside the boundary,
    // so everyone can tick games at once.
    override fun query(command: BringGame) = Query.of(
        Query.Item(setOf(GameDayCreated, GameDayEnded, GameDayCancelled),
            setOf(gameDay(command.gameDay))),
        Query.Item(setOf(PlayerJoined),
            setOf(gameDay(command.gameDay), player(command.player))),
        Query.Item(setOf(GameBrought, GameUnbrought),
            setOf(gameDay(command.gameDay), player(command.player), game(command.game))),
    )

    override fun decide(command: BringGame, state: BringState) = when {
        !state.joined -> Rejected(Rejection.NotJoined)
        command.bringing == state.bringing -> Accepted()
        command.bringing -> Accepted(GameBrought(command.gameDay, command.player, command.game))
        else -> Accepted(GameUnbrought(command.gameDay, command.player, command.game))
    }
}

2

HTML written in Kotlin

Views are plain functions in kotlinx.html, so the compiler checks them and a component is just another function. htmx swaps in one fragment per interaction, and everything still works as plain pages.

fun TagConsumer<*>.suggestions(view: TableView) = section("gf-picker__answer") {
    id = "suggestions"
    announce(view.announcement())
    when (val suggestions = view.suggestions) {
        is Suggestions.Found -> suggestions.top.forEachIndexed { i, s ->
            rankedGame(i + 1, s.game, s.reason.text())
        }
        is Suggestions.NothingFits ->
            emptyState(suggestions.title(), suggestions.text())
    }
}

3

A pure core, a thin shell

gorefest.core decides: no database, no clock, no randomness. gorefest.shell does the IO: Postgres, BoardGameGeek, mail and the web. The core is tested as given / when / then without mocks, and a test fails the build if it ever reaches for the shell.

Shell

web · Postgres · BGG · mail · clock

Core

Chapter 4 of 6

Accessible by construction

Game days happen in dim rooms, on old phones, and sometimes with a screen reader. So the code makes the inaccessible version hard to write, and the build fails when someone writes it anyway.

  1. Promised. WCAG 2.2 AA's basics are written down as obligations in the Contract, each with a test.
  2. Built in. Components like field and actionButton render the labels and ARIA, and refuse a blank name.
  3. Enforced. An architecture test fails when a view writes a raw input, button, img or aria-* itself.
  4. Checked everywhere. Every web test parses its page and checks names, unique ids, labels and heading order.

Chapter 5 of 6

One small server on Scaleway

A group of friends doesn't need Kubernetes. One fat jar on a small Scaleway instance in Paris, and every push to main is live a few minutes later.

  1. PushGitHub Actions runs every check and builds the jar.
  2. SwitchThe jar lands in a new release folder and systemd restarts.
  3. VerifyIf /health doesn't answer, it rolls back to the last release.
  4. ServeCaddy handles TLS, and pg_dump backs up nightly.

The step-by-step setup is in deploy/scaleway.md, and provision.sh does the rest on the server.

Chapter 6 of 6

How we work: Impatient Programming

Boardfest is mostly written by AI agents, following Impatient Programming: Extreme Programming for agentic development. Code is cheap. What counts is what it promises, and the checks that hold it to that.

The Contract
305 numbered promises, like GD-1 Only the host changes a game day's title, date and place. Each is proven by a tagged test, and the build fails on any promise without one.
Machines enforce the rules
A convention a machine can check goes into an architecture test, not a README. Mutation testing shows which tests actually catch anything.
Bugs are missing promises
Write the promise first, then a failing test, then the fix. Only those commits start with fix:.
Guardrails and skills
Hooks ask before a push or a risky change. Skills run the loop: story, bug, spike, an adversarial review, and exhale to simplify afterwards.

Your first hour

  1. Run it. Start Postgres with podman compose up -d, then the jar. Dev mode needs no accounts: login mail lands in /dev/mailbox.
  2. Check it. ./gradlew check runs the tests, the Contract, the architecture rules and detekt.
  3. Read two files. CLAUDE.md for the vocabulary and conventions, docs/contract/ for what the app promises.
  4. Pick a story. docs/backlog.md lists what's next.
